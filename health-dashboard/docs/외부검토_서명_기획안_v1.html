외부 검토·서명 공간 기획안 (v1, 2026-10-04)

소유자 질문: “전문가 또는 대학 등 기관에서 이 앱을 보고 인증·검증해 주는 마크나 표시를 해 주면 공신력 있겠지? 개인이 좀 더 편할 테니 인증이나 서명이 들어가는 공간이 있으면 좋을 듯한데 기획해봐.”

1. 결론 먼저

  • 공신력은 「마크」가 아니라 「누가 · 무엇을 · 어느 버전을 · 어떻게 확인했는지」가 공개될 때 생긴다. 배지 하나만 붙이면 오히려 의심받는다.
  • 그래서 「인증 마크」 대신 「외부 검토 기록」 공간을 만든다. 검토자가 서명한 의견서, 검토 범위, 검토한 버전, 발견한 문제와 우리의 조치를 함께 싣는다.
  • 개인 전문가가 가장 쉽게 참여하도록 3단계로 나눈다: ① 사용 의견(이름 공개 동의만) → ② 전문가 검토 의견서(서명) → ③ 기관 검토(공문·직인). 처음에는 ②를 2~3건 받는 것이 목표다.
  • 용어는 「인증」을 쓰지 않는다. 법정 인증 제도와 혼동되고, 실제로 한 일보다 크게 읽힌다. 「외부 검토」「자문」「검토 의견」으로 쓴다.

2. 왜 「인증」이 아니라 「검토 기록」인가

문제 「인증 마크」 방식 「검토 기록」 방식
무엇을 확인했나 알 수 없음(전부 맞다고 읽힘) 범위 칩으로 명시(예: 데이터 정확성 · 건강수명 산출법)
언제 버전인가 한 번 붙으면 계속 붙어 있음 검토한 빌드 번호·날짜 표시, 이후 변경은 「검토 이후 변경 있음」
문제를 찾았다면 감춰짐 발견 사항과 조치(정오표 번호)를 같이 공개 → 오히려 신뢰
법·윤리 법정 인증과 혼동, 기관 로고 무단 사용 위험 본인 동의 문구만, 로고는 공식 승인 있을 때만
철회 방법 없음 상태 「철회」로 바꾸고 기록은 남김

국제 공모전 심사위원에게도 「Independent review: 2 experts, scope, findings, fixes」가 배지보다 강한 근거가 된다(지시서 21절: 존재하지 않는 실적을 만들지 않는다 — 검토가 0건이면 0건이라고 쓴다).

3. 참여 3단계 — 개인이 편하게

단계 누가 하는 일 서명 방법 소요
① 사용 의견 보건소 담당자·연구자 써 본 소감 2~3문장 + 이름·소속 공개 동의 이메일 회신 「공개에 동의합니다」 10분
② 전문가 검토 교수·연구원·통계 전문가 검토 범위 1~3개를 골라 체크리스트대로 확인 → 의견서 1~2쪽 전자서명 서비스(모두싸인·DocuSign 등, 서명 이력 증명서 발급) 또는 서명 스캔 PDF 2~4시간
③ 기관 검토 대학 연구소·학회·공공기관 ②와 같은 검토를 기관 이름으로 공문(직인) 수 주
  • 검토자가 쓰기 쉽도록 의견서 서식을 화면에서 만들어 준다(아래 5.3). 이름·소속·범위·의견을 넣으면 서식이 완성되고, 복사하거나 이메일로 보내거나 인쇄해 서명한다 — 지금 「의견·문의」 탭과 같은 방식이라 서버가 필요 없다.
  • 사례비를 드리거나 공동 연구 관계가 있으면 이해관계를 함께 공개한다(예: 김동현 교수는 우리가 쓰는 DB의 제공자 → 「자료 제공자」 표시).

4. 검토 범위(체크리스트) — 「무엇을 확인했나」를 칩으로

범위 칩 검토자가 확인하는 것 화면에서 바로 하는 방법
데이터 정확성 지표 무작위 10칸을 KOSIS 원표와 대조 각 수치 옆 [n]·ⓘ → 원표 열기
지표 방향·정의 높을수록 좋음/나쁨 배정이 타당한가 지표 분석 「방향」 근거 문구, docs/지표_방향성_v1.md
순위 방법 리그·3년 평균·가중치·제외 지표 프로파일 「순위 산출 방식」, docs/랭킹_방법론_v1.md
건강수명 산출 시군구 생명표·Sullivan 계산 「산출 예시」 검산행, docs/건강수명_산출법_v1.md
지역박탈지수 변수 구성·근사의 한계 「산출 예시」, docs/지역박탈지수_산출_v2.md
우선 검토 계산 가중·등급·표본오차 처리 「계산 방법」, docs/HealthEquityRadar_설계_v1.md, npm test
표현·해석 인과 표현·과장 없음 화면 문구 전체
접근성 키보드·색 대비·휴대폰 실제 사용

검토 의견서에는 범위마다 「확인함 / 확인했으나 의견 있음 / 확인하지 않음」을 고른다. 확인하지 않은 범위는 화면에 표시하지 않는다(과장 방지).

5. 화면 설계

5.1 자리 — 세 곳

  1. 「자료원」 탭 맨 위 새 카드 「외부 검토·자문」 — 전체 기록이 있는 본문 자리. 검색 색인에도 넣는다.
  2. 모든 화면 맨 아래(제작 크레딧 위) 한 줄 — 외부 검토 2건 · 최근 2026-11-15 · 기록 보기 → (0건이면 외부 검토 기록 — 아직 없음 · 검토 참여하기 →).
  3. 해당 카드 옆 작은 표시 — 검토 범위가 그 카드와 맞을 때만. 예: 건강수명 카드 제목 옆 ✓ 방법 외부 검토 1건. 범위가 다르면 표시하지 않는다. (영문 소개 #view=radar 에도 「Independent review」 칸 — 실제 건수만.)

5.2 기록 카드 모양(예시)

┌ 외부 검토·자문 ─────────────────────────────────────────────┐
│ 이 대시보드를 외부 전문가·기관이 검토한 기록입니다. 검토 범위와 버전을 함께 적고,   │
│ 발견된 문제와 조치도 공개합니다. 「인증」이 아니라 검토 의견입니다.            │
│                                                                 │
│ ○○○ 교수 · ○○대학교 보건대학원                  2026-11-15 · 현재 유효   │
│ 범위: [데이터 정확성] [건강수명 산출]   검토 버전: 2026-11-10 빌드 #a1b2c3   │
│ "무작위 20칸을 KOSIS와 대조해 모두 일치했다. 건강수명은 근사라는 표기가…" │
│ 발견 2건 → 조치: 정오표 18·19번                                    │
│ 서명본: 전자서명 이력 증명서 보관 · 의견서 PDF ↗ · 이해관계: 없음            │
│                                                                 │
│ [검토 참여하기]  [의견서 서식 만들기]  [검토 가이드 PDF]                   │
└─────────────────────────────────────────────────────────────────┘
  • 서명 이미지는 화면에 그대로 싣지 않는다(위조에 쓰일 수 있음). 「서명본 보관 · 전자서명 이력 증명서 있음」과 의견서 PDF(서명란은 가린 판)를 싣는다.
  • 검토 이후 앱이 바뀌면 자동으로 검토 이후 변경 있음(커밋 n개)을 붙인다 — 검토한 빌드 번호와 현재 빌드 번호를 비교.

5.3 「의견서 서식 만들기」(검토자용, 서버 없음)

이름·직위·소속 → 범위 칩 선택 → 범위별 「확인함/의견 있음/확인 안 함」 + 자유 의견 → 이해관계 → 공개 동의 체크(이름·소속·의견 공개, 철회 가능) → 서식 완성:

  • 「복사」 · 「이메일로 보내기」(받는 주소 contact.json) · 「인쇄해서 서명」(A4 1~2쪽, 버전·빌드 번호·날짜 자동 기입).
  • 전자서명 서비스를 쓰는 분은 인쇄본을 PDF로 저장해 서비스에 올려 서명.

6. 데이터 구조 (서버 없이)

data/reviews.json — 소유자가 의견서를 받으면 한 줄 추가 → 빌드·배포.

{
  "reviews": [
    {
      "id": "R-2026-001",
      "type": "expert",                 // usage | expert | institution
      "name": "○○○", "title": "교수", "org": "○○대학교 보건대학원",
      "date": "2026-11-15",
      "scope": ["data", "hle"],          // 4장 범위 칩 키
      "checked": { "data": "ok", "hle": "comment" },
      "build": "a1b2c3d",                // 검토한 빌드(커밋) — 화면이 현재 빌드와 비교
      "quote": "검토자가 쓴 그대로의 문장(요약·가공 금지)",
      "findings": [{ "text": "…", "fix": "정오표 18번" }],
      "conflict": "없음",
      "proof": "esign",                   // esign | scan | official | email
      "pdf": "reviews/R-2026-001.pdf",    // docs/reviews/ (서명란 가린 판)
      "status": "current",               // current | superseded | withdrawn
      "consent": "2026-11-15 이메일"      // 공개 동의 기록
    }
  ]
}
  • 빌드 번호: build_dashboard.py 가 빌드할 때 git 커밋 해시와 날짜를 앱에 넣는다(Vite define). 화면 맨 아래와 의견서 서식에 자동 표시.
  • 원본 서명본(서명 이미지 포함)은 저장소에 올리지 않는다(공개 저장소). 소유자 보관, 요청 시 확인. 공개 PDF는 서명란을 가린 판, 그리고 원본 PDF의 SHA-256 값을 함께 적어 나중에 진본 확인이 가능하게 한다.

7. 운영 절차

  1. 초대: 검토 가이드(이 문서 4장 + 체크리스트 1쪽 PDF)와 함께 이메일. 무엇을 확인해 주면 되는지, 2~4시간 분량, 이름 공개는 선택이며 철회 가능함을 명시.
  2. 검토: 검토자가 화면에서 직접 확인 → 「의견서 서식 만들기」로 작성 → 서명.
  3. 반영: 발견 사항은 정오표(docs/사용설명서_정오표_v1.md)에 번호를 매겨 고치고, 기록에 조치 번호를 연결.
  4. 게시 전 확인: 게시될 문구를 검토자에게 보내 최종 동의를 받은 뒤 reviews.json 추가 → 배포.
  5. 갱신: 큰 변경(새 지표·새 계산) 후에는 「검토 이후 변경 있음」이 붙는다. 1년마다 재검토를 요청하고, 재검토 전 기록은 superseded로 남긴다.
  6. 철회: 검토자가 요청하면 즉시 withdrawn(이름·인용 숨김, 「철회됨」만 남김).

8. 지킬 선(법·윤리)

  • 「인증」「공인」「승인」 표현 금지 — 법정 인증과 혼동. 「외부 검토」「자문」「검토 의견」만.
  • 기관 로고·교표는 공식 사용 승인 문서가 있을 때만(대학 교표는 대부분 사용 승인 절차가 있음). 개인 검토는 로고 없이 「○○대학교 소속」 글자만.
  • 개인정보: 이름·직위·소속·의견만 공개, 연락처·서명 이미지는 비공개. 공개 동의를 서면(이메일 포함)으로 받고 기록.
  • 이해관계 공개: 사례비·공동 연구·자료 제공 관계.
  • 있는 그대로: 검토 0건이면 0건. 사용 의견(①)을 전문가 검토(②)처럼 보이게 섞지 않는다(유형별로 나눠 표시). 인용문은 검토자 문장 그대로.
  • 범위 밖으로 넓히지 않기: 「데이터 정확성」만 검토받았으면 우선 검토 계산 옆에는 표시하지 않는다.

9. 단계별 계획

단계 내용 결과물
1단계(바로 가능) 빌드 번호 표시 · reviews.json(빈 목록) · 자료원 탭 「외부 검토·자문」 카드(0건 상태 + 참여 안내) · 의견서 서식 만들기 · 검토 가이드 PDF · 푸터 한 줄 · 영문 소개 「Independent review: none yet」 화면 4곳, 문서 1건
2단계 전문가 2~3명 검토(후보 예: 건강격차 지표 세미나 발표자, 지역사회건강조사 연구자, 보건통계 전공 교수 — 자료 제공자는 이해관계 표시) 의견서 2~3건, 정오표 반영
3단계 기관 검토(대학 연구소·학회·공공기관) — 공문, 로고 승인 시 로고 표시 기관 기록 1건 이상
상시 보건소 담당자 사용 의견(①) — 별도 칸 사용 의견

1단계는 지금 구조(정적 사이트 · 서버 없음 · 「의견·문의」 서식 방식)로 하루 안에 만들 수 있다.

10. 결정이 필요한 것(소유자)

  1. 기록 카드 자리: 「자료원」 탭 맨 위(권장) vs 「의견·문의」 탭.
  2. 전자서명 서비스: 검토자에게 특정 서비스를 권할지, PDF 서명 스캔도 받을지(권장: 둘 다 받음).
  3. 첫 검토 요청 대상 2~3명.
  4. 사례비 여부(있으면 이해관계에 표시).

10-1. 소유자 결정(2026-10-04) — 1단계 구현 완료

  1. 자리: 「자료원」 탭 맨 위 카드 「외부 검토·자문」. 모든 화면 맨 아래에 「외부 검토 — 게시 N건 · 요청 진행 중 · 기록 보기 →」 한 줄, 크레딧 줄에 빌드 번호.
  2. 검토 요청은 이미 보냄 → data/reviews.json pending.active: true, 화면에는 검토자 이름 없이 「검토 요청 진행 중」만. 동의를 받으면 reviews에 추가하고, 다 끝나면 pending.active: false.
  3. 사례비 없음 — 「무보수 자원 검토」를 원칙 문구와 의견서 서식 이해관계 기본값에 명시(policy.paid: false).
  4. 서명: 전자서명 PDF·서명 스캔 둘 다 받음(서식의 「인쇄해서 서명」 → PDF 저장 가능).
  5. 검토자용 안내: docs/외부검토_가이드_v1.md(카드의 「검토 참여 가이드 ↗」).
