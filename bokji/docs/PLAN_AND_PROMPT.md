# 모두의 복지 AI — 공공 AI 대전환 챌린지용 신규 기획서 + Claude Code 개발지시서

## 1. 제품 한 줄
**“내 상황을 말하면, 받을 가능성이 있는 복지·돌봄·생활지원 서비스를 쉬운 말로 정리하고, 오늘 무엇을 해야 하는지까지 알려주는 취약계층용 공공서비스 길잡이.”**

서비스명(가칭): **모두의 복지 AI**
부제: **말하면 찾아주고, 순서대로 알려주는 복지 길잡이**

---

## 2. 이 서비스가 해결할 문제

기존 정부 서비스에는 이미 복지로의 맞춤형급여안내(복지멤버십), 정부24의 혜택알리미가 존재한다.
따라서 “복지서비스를 찾아준다”만으로는 신규성이 약하다.

이 서비스는 기존 서비스를 대체하지 않고 **복지정보를 이해하고 실제 행동으로 옮기는 마지막 1마일(last mile)**을 해결한다.

대상:
- 고령자
- 장애인
- 독거가구
- 저소득 가구
- 디지털 취약자
- 보호자/가족
- 외국인·저문해 사용자(후속)

핵심 문제:
1. 복지제도 이름 자체가 어렵다.
2. 어디에서 신청하는지 모른다.
3. 여러 서비스를 동시에 받을 수 있는지 모른다.
4. 본인 상황을 행정용어로 바꾸기 어렵다.
5. 보호자가 대신 알아보는 경우 정보가 흩어져 있다.
6. “받을 수 있는지”와 “지금 무엇을 해야 하는지”가 분리돼 있다.

---

## 3. 차별점

### 기존 서비스
- 복지로: 받을 가능성이 있는 서비스를 찾아 안내
- 정부24 혜택알리미: 본인 상황에 따른 혜택 탐색

### 모두의 복지 AI
**검색 서비스가 아니라 행동지원 서비스**

사용자가 말한다:
> “78세 어머니가 혼자 사시고 무릎이 안 좋아 병원 가기 힘듭니다.”

시스템은 결과를 다음 순서로 보여준다.

1. **먼저 확인할 지원**
2. **왜 이 지원을 확인해야 하는지**
3. **신청기관**
4. **준비할 것**
5. **전화/방문/온라인 중 가능한 방법**
6. **오늘 할 일 1·2·3**
7. **공식 사이트로 이동**
8. **가족에게 보내기**

중요:
- 최종 수급자격을 AI가 판정하지 않는다.
- “가능성이 있음 / 확인 필요 / 현재 정보로 판단 어려움”으로 표현한다.
- 최종 판단은 담당기관이 한다.

---

## 4. MVP 대상

처음부터 모든 복지제도를 넣지 않는다.

### MVP 대상군
**노인 + 장애인 + 보호자**

### MVP 서비스 분야
1. 노인맞춤돌봄
2. 기초연금
3. 장기요양 인정·이용 안내
4. 장애인연금/장애수당
5. 장애인 활동지원
6. 이동지원
7. 방문건강관리
8. 의료비/건강보험 본인부담 관련 공식 지원
9. 에너지·생활비 감면
10. 응급·위기상황 연락처

실제 공식 원문과 링크가 확인된 항목만 노출한다.

## 5. 사용 흐름

### 화면 1 — “무엇이 필요하신가요?”
큰 마이크 버튼 + 큰 글씨 입력

예시 버튼:
- 혼자 사는데 도움이 필요해요
- 병원 가기 어려워요
- 돈이 부족해요
- 장애가 있어 생활이 불편해요
- 부모님이 받을 수 있는 지원을 찾고 싶어요

### 화면 2 — 필요한 최소 질문
최대 5~7개만 묻는다.

예:
- 본인/가족 중 누구를 위한 것인가?
- 나이대
- 거주 지역
- 혼자 거주 여부
- 장애 등록 여부
- 장기요양 등급 여부
- 가장 필요한 도움

소득/재산 등 민감정보는 초기 MVP에서 받지 않는다.
정밀 자격판정이 필요한 경우 “공식 확인 필요”로 안내한다.

### 화면 3 — 결과
#### 지금 먼저 확인할 지원
카드 최대 3개

각 카드:
- 서비스명
- 한 줄 설명
- 확인 가능성: 높음 / 확인 필요
- 신청기관
- 신청방법
- 필요한 기본 서류
- 공식 링크
- 129 또는 해당 기관 전화

### 화면 4 — 오늘 할 일
예:
1. 주소지 행정복지센터에 전화
2. 장기요양 인정 여부 확인
3. 복지로에서 맞춤형급여안내 가입 여부 확인

### 화면 5 — 보호자에게 보내기
- 카카오톡용 텍스트 복사
- 문자용 요약
- 인쇄
- 큰 글씨 보기
- 음성 읽기

## 6. 접근성

반드시 구현:
- 기본 글자 18px 이상
- 초대형 글자 모드
- 음성 읽기(TTS, 브라우저 SpeechSynthesis 가능)
- 버튼 터치영역 44px 이상
- 키보드 사용
- 고대비
- 색만으로 상태 표현하지 않기
- 쉬운 한국어
- 한 화면 한 행동
- “뒤로” 버튼 명확히
- 자동 로그아웃/개인정보 저장 없음

후속:
- 수어 영상 연결
- Easy Read pictogram
- 다국어

## 7. AI는 어디에 쓰나

AI를 억지로 강조하지 않는다.

### AI 사용
- 사용자의 자연어 상황을 구조화된 요구로 변환
- 어려운 복지제도 설명을 쉬운 말로 변환
- 서비스 후보를 검색·정렬
- 사용자의 상황에 맞춰 “오늘 할 일” 순서를 제시

### AI가 하지 않는 것
- 법적 수급자격 확정
- 의료진단
- 재산/소득 자동판정
- 허위 서비스 생성
- 공식 근거 없는 신청 가능성 단정

### 안전 구조
**공식 데이터 → 규칙 필터 → AI 쉬운 설명 → 공식 원문 링크**

LLM이 새로운 복지제도를 만들어내지 못하게 서비스 목록은 화이트리스트 기반으로 한다.

## 8. 데이터 구조

`services.json` 예시:

```json
{
  "id": "elderly-care",
  "name": "노인맞춤돌봄서비스",
  "target_tags": ["older_adult", "living_alone", "daily_living_support"],
  "age_min": 65,
  "conditions": {
    "requires_official_check": true
  },
  "summary_easy": "혼자 생활하기 어렵거나 돌봄이 필요한 어르신에게 안전 확인과 생활 지원을 제공합니다.",
  "apply": {
    "channel": ["행정복지센터", "공식 온라인 서비스"],
    "phone": "129"
  },
  "official_url": "...",
  "source_org": "보건복지부",
  "verified_at": "2026-10-06"
}
```

모든 서비스에:
- source_org
- official_url
- verified_at
- eligibility_note
- last_checked
를 필수로 둔다.

## 9. 추천 엔진

초기 MVP는 완전한 생성형 AI 판정이 아니라 규칙 기반이다.

### Step 1
사용자 답변 → tags

예:
`age_65_plus`, `living_alone`, `mobility_issue`, `caregiver_query`

### Step 2
서비스 후보 필터

### Step 3
우선순위 점수
- 상황 직접 관련성
- 긴급성
- 신청 가능성 확인 필요 정도
- 접근성

### Step 4
AI는 카드 설명만 쉬운 말로 바꾼다.

## 10. 데모 시나리오

### 시나리오 A — 독거노인
입력:
> “78세 어머니가 혼자 사는데 무릎이 아파 병원에 혼자 못 갑니다.”

결과:
- 노인맞춤돌봄서비스
- 장기요양 인정 신청 확인
- 지역 이동지원/교통지원 확인
- 방문건강관리 확인

오늘 할 일:
1. 129 또는 행정복지센터에 노인맞춤돌봄 상담
2. 장기요양 인정 여부 확인
3. 지역 이동지원서비스 확인

### 시나리오 B — 장애인 보호자
입력:
> “성인 발달장애 자녀가 있고 낮 시간 돌봄이 필요합니다.”

결과:
- 장애인 활동지원
- 발달장애인 주간활동서비스
- 보호자 지원 정보
- 지역 발달장애인지원센터

### 시나리오 C — 경제·생활 위기
입력:
> “혼자 사는데 최근 소득이 줄고 전기요금이 부담됩니다.”

결과:
- 복지멤버십 가입 확인
- 에너지 관련 지원

# Claude Code 개발 지시

당신은 공공서비스 접근성과 React 웹 개발 경험이 있는 시니어 개발자다.

## 목표
7일 이내 경진대회 데모 가능한 모바일 우선 웹 MVP를 만든다.

### 기술
- React + Vite
- 정적 JSON 기반
- 서버/로그인 없음
- 개인정보 저장 없음
- 브라우저 TTS
- 배포: GitHub Pages 또는 Vercel

### 첫 화면
- 서비스명
- 큰 마이크 아이콘
- 큰 입력창
- 예시 질문 4개
- “말하거나 입력해 주세요”

### 필수 페이지
1. Home
2. Situation Questions
3. Recommendation
4. Service Detail
5. Today Action Plan
6. Accessibility settings
7. Sources / limitations

### MVP에서는 실제 LLM API 없이도 동작하게 만들 것
키워드 + 규칙 엔진으로 3개 데모 시나리오가 완전히 작동해야 한다.

LLM 연동은 adapter interface로 분리:
`interpretSituation(text)`

API 키가 없으면 deterministic fallback이 동작해야 한다.

### 데이터
`src/data/services.json`
`src/data/demoCases.json`

실제 공식 서비스 URL이 확인되지 않은 항목에는 가짜 URL을 만들지 말고 `official_url: null`, 화면에는 “공식 링크 확인 중”이라고 표시.

### 추천 결과
최대 3개의 우선 서비스 + 추가로 확인할 서비스.

상태:
- “먼저 확인해 보세요”
- “조건 확인이 필요합니다”
- “현재 정보만으로 판단하기 어렵습니다”

“받을 수 있습니다” 금지.

### 접근성
- 18px 이상
- 큰 글씨 모드
- TTS
- 고대비
- WCAG AA 목표
- tab navigation
- aria labels
- 44px touch target

### 보호자 모드
Home에서:
- 나를 위한 도움
- 가족을 위한 도움

둘 중 선택.

### 결과 공유
- Copy
- Print
- 문자용 요약 복사
- 개인정보 포함 금지

### 안전문구
항상 결과 하단에:
“이 서비스는 복지급여 수급자격을 최종 판정하지 않습니다. 실제 대상 여부와 신청 결과는 담당기관의 확인이 필요합니다.”

### 디자인
- 공공기관 느낌이지만 딱딱하지 않게
- 고령자가 보기 쉬운 흰 배경 + 높은 대비
