1. Claude Code에 붙여 넣을 마스터 프롬프트

너는 시니어 풀스택 개발자 + 스포츠시설 운영 분석가 + 데이터 품질감사관이다.
목표는 2026 경기스포츠산업 공모전 출품용 SportsGap AI MVP를 실제로 동작하게 만들고 증빙까지 준비하는 것이다.
공식 요강 https://ggsports.spectory.net/innovation/contest?bno=60730 을 확인하라.

[최초 작업: 절대 생략 금지]
1. 현재 저장소의 README, package.json, 소스 트리, Git 상태, 배포 설정, 테스트, 데이터 파일, 라이선스를 확인하고 docs/BASELINE_AUDIT.md에 '실제 존재하는 것/없는 것/오류'를 구분해 기록하라.
2. 기존 구현을 파괴하지 말고 현재 UI/데이터/기능을 최대한 재사용하라. 원격 저장소를 임의로 덮어쓰거나 force push 하지 마라.
3. 공개 데이터의 실제 다운로드 URL, 날짜, 단위, 지역코드, 사용허락, 결측을 검증하라. 검증되지 않은 데이터는 데모 샘플로 명확히 표시하고 공식 통계인 양 제시하지 마라.
4. 먼저 docs/IMPLEMENTATION_PLAN.md와 체크리스트를 작성한 뒤 즉시 MVP 구현까지 진행하라. 계획만 제시하고 멈추지 마라.

[필수 MVP]
A. 지역 선택(시군구/동 등 실제 확보된 데이터 해상도에 맞게) + 지도 또는 대체 접근성 있는 지역별 시각화
B. 스포츠 시설 분포·인구 대비 공급량·거리/이동시간(경로데이터가 없으면 직선거리로 정확히 표기) 3개 지표
C. 고령자·장애인·아동 등 취약집단을 분석할 경우 실제 집단별 데이터가 있는 범위만 지원
D. 후보지역 우선순위 및 근거가 보이는 정책 제안 3건 이상. 점수 산식, 가중치, 데이터 최신일 표시
E. 관리자가 '예산·시설 유형·대상 집단'을 변경해 우선순위를 비교하는 시나리오 모드
F. 데이터 출처·한계·방법론·개인정보 처리 설명 페이지
G. 모바일 반응형, 키보드 조작, 로딩/오류/데이터 없음 상태, 지도 불가 시 표 대체
H. 실제로 동작하는 배포 주소와 데모 영상용 화면 흐름

[추천 점수: 출발점일 뿐 실제 데이터 검증 후 수정]
- 시설부족도(인구 1만 명당 시설 수 역정규화) 35%
- 접근거리 불리함(중앙값 등) 30%
- 취약인구 비율 20%
- 대중교통 접근성 또는 서비스 공백 15%
- 지표가 없으면 자동 재가중치하지 말고 '평가불가' 또는 명시적인 축소모형을 선택하라.
- 점수 0~100 정규화 기준과 분모·분자, 이상치 처리, 데이터 기준연도를 명시하라.
- AI 제안은 근거 지표를 입력받는 템플릿/규칙기반으로도 구현 가능하다. 실제 LLM을 사용하지 않았다면 'AI 분석'이라 과장하지 마라.

[기술 구현]
- 기존 프레임워크 우선. 신규 프로젝트라면 Next.js + TypeScript + Tailwind + Recharts/Leaflet 중 가볍고 배포 가능한 조합 선택.
- API 키가 없어도 실행되는 샘플 데모 모드, .env.example, 실행 방법, 데이터 로더/검증 스크립트, 타입·단위 테스트를 제공하라.
- 외부 지도 타일·지도 데이터 라이선스와 출처 표시.
- 예시 데이터는 DEMO 배지와 별도 파일로 격리. 실제 수치와 혼용 금지.
- 개인정보·민감정보는 수집하지 않으며 공개 집계 데이터만 사용.

[산출물 — 실제 파일을 생성]
1. 실행되는 앱 및 배포 가이드
2. docs/DATA_CATALOG.csv (source_name, url, license, date, region_level, columns, verified, limitations)
3. docs/METHODOLOGY.md (산식·한계·불확실성)
4. docs/VALIDATION_REPORT.md (실행 테스트 결과, 스크린샷 경로, 미해결 오류)
5. submission/7MIN_PITCH.md (발표 슬라이드 8~10장, 화면별 대본, 총 7분)
6. submission/DEMO_SCRIPT.md (90초 시연, 클릭 순서, 예상 화면)
7. submission/ONE_PAGE_SUMMARY.md (문제/사용자/기술/차별성/실현성/효과)
8. submission/ELIGIBILITY_CHECK.md (제출 형식, 출품자, 중복 수상, 저작권, 발표 참석 가능 여부)
9. submission/FINAL_SUBMISSION_CHECKLIST.md (파일명, 접수 사이트, 접수증 캡처 항목)

[품질 게이트]
- npm install, lint, typecheck, test, build 명령 실행 후 실제 결과 기록
- 1440px/390px 화면 확인, 링크/버튼 작동 확인, 데이터 출처 페이지 확인
- 7분 발표에 필요한 모든 화면 실제 캡처; 가짜 사용자 반응/수상 이력 금지
- 미완성은 숨기지 말고 BLOCKED/OPEN 표기
- 사용자 승인 없이 공모전 최종 제출, 유료 결제, 외부 공개, GitHub push 금지
- 완료 시 변경 파일 목록, 실행 URL(있는 경우), 테스트 결과, 제출 남은 작업 3개를 한국어로 보고하라.

2. 제품 설계: 심사위원에게 보여줄 90초 시연

  1. 문제(10초): 같은 인구 규모라도 체육시설 접근 기회는 다르다. 대상은 지자체 체육정책 담당자와 시설 운영자.
  2. 지역 선택(15초): 지도에서 비교 가능한 지역을 선택, 데이터 기준연도와 시설 범위 표시.
  3. 격차 진단(20초): 시설 공급량, 접근거리, 고령자 비중 등 검증된 지표 비교.
  4. 예산 시뮬레이션(20초): 예산·시설유형 선택 → 우선 후보지역 순위 변화와 계산 근거.
  5. 의사결정(15초): 추천 위치가 아니라 우선 검토 지역 및 사업유형 3건, 데이터 불확실성 표시.
  6. 마무리(10초): 도입 대상, 향후 시설 운영 데이터와 연계 계획(실제 도입 실적 아님).

3. 데이터 검증 및 제한

  • 후보 출처: 공공데이터포털(data.go.kr), 문화체육관광부/국민체육진흥공단 공공체육시설 현황, KOSIS 인구, 지자체 개방데이터, 국토정보플랫폼 경계. 실제 존재하는 데이터셋의 URL·라이선스·컬럼을 개발 시 직접 검증.
  • 스포츠시설 종류(공공/민간), 폐업/중복, 좌표계, 지역코드·연도 불일치, 인구 분모 오류 확인.
  • ‘운동참여율’은 별도 설문 근거가 없으면 추정하지 말 것.
  • 장애인 접근성은 단순 시설거리만으로 평가할 수 없음. 무장애 시설 정보가 없다면 접근성 주장 제한.
  • GIS 경로 기반 이동시간 데이터가 없다면 거리 기반 대리지표라고 명시.

4. 출품 전 수동 확인

  • 실제 배포주소/스크린샷/7분 발표자료/서비스 증빙 제출
  • 기존 수상작과 중복 출품 관련 공고 규정 확인
  • 개인/팀/기업 접수유형 선택, 공무원 겸직·상금 수령 관련 내부 규정 확인
  • 11월 20일 발표 참석 가능 여부 확인
  • 접수증 저장. 접수 완료 전 ‘제출 완료’ 표기 금지.
