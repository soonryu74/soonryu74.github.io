# 하트가드 — 심박 이상 안심 알림 시제품 구축 기획서

작성일: 2026-11-10
근거: 인수인계서(HANDOFF.md, 2026-11-10) + 사용자 확인 답변
상태: 기획 확정, 코드 없음

---

## 0. 확정된 전제

| 항목 | 확인 결과 | 기획에 미치는 영향 |
|---|---|---|
| 워치 | 가민/코로스/폴라 계열 | 표준 심박수 전송으로 실기기 연결까지 1단계에 포함 |
| 폰 | 안드로이드 | 폰 크롬 하나로 착용자 시연 가능 |
| 보호자 알림 | 웹 푸시로 시작 | 문자·알림톡은 2단계 |
| 공모전 마감 | 미정 | 단계마다 "여기서 멈춰도 시연 가능"하게 자른다(6장) |

아직 모르는 것: 워치의 정확한 모델명. 심박수 전송 메뉴 위치와 "벗었을 때 오는 값"이 모델마다 달라서 4단계 전에 필요하다.

## 1. 이 시스템이 할 수 있는 것과 없는 것

신뢰는 "못 하는 것을 숨기지 않는 것"에서 나온다. 화면·문서·발표 자료에 아래를 그대로 쓴다.

**할 수 있는 것**
- 워치가 보내는 심박수가 비정상으로 낮아지거나 급락했는데 본인이 30초 안에 응답하지 않으면, 보호자에게 시각·마지막 심박·위치를 알린다.
- 본인이 직접 SOS를 누르면 즉시 보호자에게 알린다.
- 모든 상태 변화를 기록해 오경보가 언제, 왜 났는지 분석할 수 있게 한다.

**할 수 없는 것 (설계로 해결되지 않는 한계)**
1. **심장정지를 감지하지 못한다.** 손목 광학 센서는 맥박이 사라지면 "0"이 아니라 값 전송 중단이나 엉뚱한 값을 내는 경우가 많다. 이 경우 시스템은 "연결 끊김" 또는 "미착용"으로 본다. 즉 가장 위험한 상황이 경보로 이어지지 않을 수 있다. 이것이 고지문("응급 상황을 놓칠 수 있습니다")의 실제 의미다.
2. **화면이 꺼지면 멈춘다.** 웹앱은 폰 화면이 켜져 있고 탭이 앞에 있을 때만 동작한다. 일상 상시 감시는 2단계(워치 전용 앱)의 일이다.
3. **폰에 인터넷이 없으면 보호자에게 갈 수 없다.** 이때는 폰 자체 경보음과 "119 전화하기" 버튼만 동작한다.
4. **웹 푸시는 도착이 보장되지 않는다.** 보호자 폰의 절전 설정, 알림 차단에 따라 늦거나 안 올 수 있다.

따라서 이 시제품의 주장 범위는 "알림 경로가 끝까지 동작한다 + 오경보를 이렇게 줄였다 + 그 데이터를 모았다"까지다. 판정 성능 수치는 만들지 않는다.

## 2. 전체 구조

```
[워치] --블루투스 심박(0x180D)--> [착용자 웹앱: 안드로이드 크롬]
                                      |  판정은 전부 폰 안에서
                                      |  (서버가 죽어도 본인 확인·경보음·119 버튼은 동작)
                                      v
                               [Supabase]
                        DB + 서버 함수 + 예약 작업
                          |                |
                 현재 상태 조회        웹 푸시 발송
                          v                v
                    [보호자 페이지: 아무 폰·브라우저]
```

핵심 원칙 세 가지:
- **판정은 폰에서, 전달은 서버에서.** 심박 원자료는 폰을 떠나지 않는다. 서버에는 상태 변화와 경보만 간다.
- **알림 경로는 이중으로.** 보호자 페이지 화면 표시(조회)와 웹 푸시(밀어 보냄)를 둘 다 쓴다. 하나가 실패해도 다른 하나가 남는다.
- **모의와 실제는 같은 길을 탄다.** 모의 모드는 심박 "입력"만 가짜로 바꾸고 판정·알림·기록은 실제와 같은 코드를 쓴다. 그래야 시연이 곧 검증이 된다. 단, 모의 경보는 보호자 화면과 푸시에 "[모의]"를 붙인다.

## 3. 신뢰성 설계 (인수인계서에 더하는 부분)

### 3.1 경보가 중간에 사라지지 않게 — 서버 예약 경보

문제: 본인 확인 30초가 끝나는 순간 폰이 꺼지거나 통신이 끊기면 경보가 영영 안 간다.

해결:
1. "의심"에 들어가는 순간 폰이 서버에 **예약 경보**를 등록한다(발동 예정 시각 = 지금 + 30초 + 여유 10초).
2. "괜찮아요"를 누르면 예약을 취소한다.
3. 30초가 지나면 폰이 직접 경보를 확정한다(정상 경로).
4. 폰이 확정도 취소도 못 한 채 예정 시각이 지나면 서버가 대신 발동한다(예비 경로). 이때 보호자에게는 "착용자 폰과 연락이 끊긴 상태에서 발동됨"이라고 표시한다.

완료 기준 "괜찮아요를 누르면 보호자에게 아무것도 가지 않음"을 지키기 위해, 예약 단계의 정보는 보호자 페이지에 노출하지 않는다.

남는 한계: 취소 요청이 통신 문제로 서버에 못 닿으면 오경보가 한 번 나갈 수 있다. 놓치는 것보다 낫다고 보고 이 방향을 택하며, 기록에 사유를 남긴다.

### 3.2 보호자 접근 — 초대 링크는 서버 함수로만

초대 링크를 가진 사람은 로그인 없이 봐야 하므로, 테이블을 직접 읽게 열지 않는다.
- 모든 테이블은 행 수준 보안을 켜고 **익명 직접 읽기는 전부 막는다.**
- 보호자 페이지는 서버 함수 하나(`guardian_view(token)`)만 호출한다. 함수는 토큰이 맞을 때만 현재 상태와 진행 중인 경보를 최소 항목으로 돌려준다.
- 초대 토큰은 추측 불가능한 긴 무작위 값, 착용자가 설정에서 폐기·재발급 가능.
- 보호자 페이지는 **3초마다 조회**한다. 실시간 채널보다 단순하고, 연결이 끊겨도 스스로 회복하며, 완료 기준(10초 안 표시)을 여유 있게 만족한다.
- 보호자의 "확인했어요(해제)"도 같은 방식의 서버 함수(`guardian_ack(token, alert_id)`)로 처리한다.

### 3.3 착용자 로그인 — 가입 없이 익명 계정

Supabase 익명 로그인으로 기기마다 계정을 자동 발급한다. 이름만 입력받는다. 폰을 바꾸거나 브라우저 데이터를 지우면 기록이 이어지지 않는데, 시제품 범위에서는 받아들이고 설정 화면에 안내한다.

### 3.4 "살아 있음" 신호

착용자 앱이 30초마다 현재 상태 한 줄(상태, 갱신 시각)을 덮어쓴다. 쌓지 않고 덮어쓰므로 "초 단위로 쌓지 않는다"는 원칙과 충돌하지 않는다.
- 보호자 페이지는 갱신이 90초 넘게 없으면 "착용자 앱이 꺼져 있거나 연결 확인이 안 됩니다"를 회색으로 표시한다. **경보가 아니다.**
- 이 표시가 없으면 보호자는 "정상"이 진짜 정상인지 앱이 꺼진 건지 구분할 수 없다.

### 3.5 브라우저 제약 대응

| 제약 | 대응 |
|---|---|
| 소리는 사용자가 한 번 눌러야 재생 가능 | 고지문 "동의" 버튼을 누를 때 소리 재생 권한을 함께 연다. 시작 화면에 "경보음 미리 듣기" 버튼 |
| 웹은 폰 음량을 바꿀 수 없음 | "최대 음량"은 구현 불가. 시작 화면에서 "미디어 음량을 올려 주세요" 안내 + 미리 듣기로 확인 |
| 위치 확인에 수 초 걸림 | 권한은 시작 때 받고, 위치 조회는 "의심" 진입 순간 시작해 둔다. 서버 저장은 경보 확정 때만. 실패하면 "위치 확인 실패"로 경보는 그대로 발송 |
| 화면 꺼짐 | 화면 켜짐 유지(Wake Lock) + 탭이 다시 보일 때 재획득. 탭이 뒤로 간 시간은 "감시 중단"으로 기록 |
| 블루투스 끊김 | 끊김 감지 시 자동 재연결(간격을 늘려가며). 일부 환경에서는 사용자가 다시 눌러야 하므로 "다시 연결" 큰 버튼 병행 |
| 아이폰 보호자의 웹 푸시 | 홈 화면에 추가해야 푸시 수신 가능. 보호자 페이지에 폰 종류별 안내. 푸시가 안 되어도 페이지를 열어 두면 경보는 보인다 |

### 3.6 오경보 억제

인수인계서 7장 표를 그대로 구현하되 아래를 더한다.
- **의심 판정에는 "연속으로 유효한 값"이 필요하다.** 값이 드문드문 올 때는 의심이 아니라 연결 끊김 쪽으로 본다.
- **급락 규칙(15초 내 50% 이상)은 기본값을 "기록만" 으로 시작**하는 선택지를 설정에 둔다. 달리기 중 손목 센서는 순간적으로 값이 튀는 일이 흔해서, 실측 전에는 이 규칙이 오경보의 주범이 될 가능성이 있다. 실측 데이터를 본 뒤 켠다. (8장에서 확정)
- 경보 해제 후 2분간은 같은 사유로 다시 의심에 들어가지 않는다(반복 경보 방지). SOS는 예외.
- 모든 판정에 사유 코드를 붙여 기록한다(예: `LOW_HR_SUSTAINED`, `SUDDEN_DROP`, `MANUAL_SOS`, `SERVER_FALLBACK`).

## 4. 데이터 구조 (인수인계서 8장 수정안)

| 테이블 | 내용 | 변경점 |
|---|---|---|
| `profiles` | 사용자 id, 표시 이름 | 그대로 |
| `guardians` | 사용자 id, 보호자 이름, 초대 토큰(해시 저장), 푸시 구독 정보, 폐기 시각 | 토큰 해시 저장, 폐기 추가 |
| `live_status` | 사용자 id(1인 1행), 현재 상태, 갱신 시각, 모의 여부 | **신규** — 보호자의 "현재 상태"용 |
| `events` | 사용자 id, 시각, 이전 상태, 새 상태, 심박, 사유 코드, 모의 여부 | 사유를 코드로 |
| `alerts` | 사용자 id, 단계(예약/확정/취소/해제), 발동 예정 시각, 시작·해제 시각, 해제한 사람, 위도·경도, 마지막 심박, 발동 경로(폰/서버), 모의 여부 | 단계·예정 시각·경로 추가 |

보관: 위치는 경보 해제 30일 뒤 자동 삭제. 사용자가 설정에서 "내 기록 전부 삭제"를 할 수 있다. 공모전 제출용 통계는 CSV로 내보낸 익명 집계만 쓴다.

서버 구성: 서버 함수 3개(`guardian_view`, `guardian_ack`, 푸시 발송) + 예약 작업 1개(예정 시각이 지난 예약 경보 발동, 10초 간격).

> 확인 필요: Supabase 무료 플랜에서 10초 간격 예약 작업과 익명 로그인 한도는 5단계 착수 시점에 공식 문서로 다시 확인한다. 안 되면 예비 경로 간격을 1분으로 늘린다(정상 경로는 영향 없음).

## 5. 판정 엔진 설계

- 입력: 시각이 붙은 사건(심박 수신, 연결 해제, 사용자 응답, SOS, 시간 경과). 출력: 새 상태와 "해야 할 일" 목록(경보음, 예약 등록, 기록 등).
- 시계와 통신을 엔진 밖에 두어, 테스트에서 30초를 실제로 기다리지 않고 검증한다.
- 임계값은 설정 파일 한 곳. 모의 시나리오도 같은 형식의 사건 목록이라 테스트와 시연이 같은 자료를 쓴다.

필수 테스트(완료 기준과 1:1 대응):

| 시나리오 | 기대 결과 |
|---|---|
| 정상 70 → 25가 10초 지속 → 무응답 30초 | 경보 1회, 예약 등록 후 확정 |
| 같은 상황에서 20초에 "괜찮아요" | 경보 0회, 예약 취소, 기록 남음 |
| 수신이 10초 이상 멈춤 | 연결 끊김, 경보 0회 |
| 접촉 미감지 또는 0 반복 | 미착용, 경보 0회 |
| SOS 3초 길게 누름 | 본인 확인 없이 즉시 경보 |
| 급락 직후 연결 끊김 | 본인 확인을 계속 진행, 무응답 시 경보 |
| 해제 직후 같은 사유 재발 | 2분간 재진입 없음 |
| 16비트 심박값, RR 간격 포함·미포함, 접촉 정보 없음 | 수신 해석 정확 |

## 6. 작업 순서와 멈춤 지점

각 단계 끝에서 "눌러서 확인할 것 3줄"을 전달한다. 굵은 줄에서 멈춰도 시연이 된다.

| 단계 | 내용 | 끝나면 되는 것 |
|---|---|---|
| 1 | 프로젝트 뼈대, 모의 모드(정상·급락·끊김·미착용) | 워치 없이 심박 숫자가 움직임 |
| 2 | 판정 엔진 + 단위 테스트 | 5장 표 통과 |
| 3 | 메인·본인 확인·경보 화면, 기록·CSV | **멈춤 지점 A: 폰 한 대로 전 과정 시연(서버 없음)** |
| 4 | 블루투스 연결·수신 해석, 실기기 실측 | 실제 워치 심박이 1~2초 간격 표시. 벗었을 때 값 실측 → 7장 표 보정 |
| 5 | Supabase: 익명 로그인, 기록, 보호자 초대·페이지, 예약 경보 | **멈춤 지점 B: 폰 두 대 시연(착용자 → 보호자 화면 10초 내)** |
| 6 | 웹 푸시 | 보호자 폰이 잠겨 있어도 알림 |
| 7 | GitHub Pages 배포, 실기기 점검, 오경보 수집 운영 | **완성: 인수인계서 11장 완료 기준 전부** |

4단계를 5단계보다 먼저 두는 이유: 실기기 실측 결과가 판정 표를 바꿀 수 있어서, 서버에 기록 형식을 굳히기 전에 확인한다.

### 실기기 실측 계획 (4단계, 사용자와 함께)

같은 워치로 아래를 각 3회 반복하고 앱의 기록을 CSV로 받는다.
1. 가만히 착용 5분 — 수신 간격, 값 안정성
2. 워치를 벗어 책상에 둠 — 0이 오는가, 전송이 멈추는가, 마지막 값이 유지되는가
3. 워치를 느슨하게 참 — 값이 튀는 정도
4. 폰에서 10m 이상 멀어짐 — 끊김 감지까지 걸리는 시간, 돌아왔을 때 자동 재연결
5. 가벼운 달리기 10분 — 급락 규칙이 잘못 울리는 횟수

이 5가지 결과가 곧 공모전 자료의 "오경보를 이렇게 줄였다" 근거가 된다.

## 7. 위험 요소와 대비

| 위험 | 가능성 | 대비 |
|---|---|---|
| 보유 워치가 심박수 전송을 지원하지 않음 | 중 | 모델명 확인 후 판단. 안 되면 가슴 스트랩 심박계(2~4만 원대)로 대체 — 같은 표준이라 코드 변경 없음 |
| 시연장에서 블루투스·통신 불안정 | 중 | 모의 모드가 같은 경로를 타므로 그대로 전환. 시연 영상 사전 녹화 |
| 급락 규칙 오경보 다발 | 높음 | "기록만" 모드로 시작(3.6) |
| 푸시 미도착 | 중 | 보호자 페이지 조회가 주 경로, 푸시는 보조로 설명 |
| 초대 링크 유출 | 낮음 | 폐기·재발급, 노출 항목 최소화, 위치는 경보 중에만 |
| 의료기기 오인 | 중 | 용어 고정("심박 이상 안심 알림"), 고지문 2곳, 성능 수치 미기재 |

## 8. 결정 사항

확정 (2026-11-10 사용자 확인):

| 항목 | 결정 |
|---|---|
| 코드 위치·배포 | 이 저장소의 `heartguard/` 폴더, GitHub Pages(`soonryu74.github.io/heartguard`). Vercel은 쓰지 않는다. Supabase는 새 프로젝트 |
| 급락 규칙 초기 동작 | "기록만"으로 시작. 실기기 실측 뒤 켠다. "심박 30 미만 10초 지속" 규칙은 처음부터 경보 |
| 급락 직후 연결 끊김 | 본인 확인을 계속 진행한다 |

배포 방식에 따른 반영: 빌드 결과물만 `heartguard/`에 두고 소스·테스트·의존성은 `_config.yml`의 제외 목록에 추가한다(기존 caregap과 같은 방식).

남은 것:
- **워치 모델명**: 4단계 전까지 알려주면 된다.
