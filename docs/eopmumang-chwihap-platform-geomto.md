# 업무망용 문서 공동편집·수정이력·취합 플랫폼 개발 검토 보고서

- 작성일: 2026-09-23
- 검토 대상: 인터넷이 끊긴 업무망(폐쇄망)에서 쓰는 ① 구글 시트·독스식 공유작업 ② 쉬운 수정이력 확인 ③ 취합 업무(예: ○○년도 지침 개정 취합)를 지원하는 도구
- 검토 방식: 전문가 관점 5인(보안, 아키텍처, 현업 실무, UX, 사업화)의 독립 검토를 종합

---

## 1. 결론

| 항목 | 판정 |
|---|---|
| 기술적으로 개발 가능한가 | **가능 (중상)** |
| 실제 기관에 도입될 가능성 | **중.** HWP 입출력과 신구대비표를 갖추면 상 |
| 제품으로 직접 판매 | **하** (GS인증, 조달, 유지보수 부담) |
| 강의·유튜브 소재 | **상** |

**전문가 5인의 공통 결론:** 편집기를 새로 만들 게 아니라 **"조문 단위 취합 + 신구대비표 자동생성"**에 집중해야 합니다. 편집기는 한컴독스나 OnlyOffice를 이길 수 없지만, 취합 흐름은 지금 시장에 비어 있습니다.

## 2. 구현 방식 비교

| 방식 | 내용 | 판정 |
|---|---|---|
| A. 오픈소스 설치형 | Nextcloud + OnlyOffice(LDAP 연동) 위에 취합 기능만 플러그인으로 개발 | 중상. 보안 전문가 권고안 |
| B. 자체개발(축소형) | TipTap + Yjs + Hocuspocus + PostgreSQL로 조문 블록 구조를 만들고 제안 카드 방식 적용 | 중상. 아키텍트 권고안 |
| C. 공유폴더 + HTML 단일파일 | 서버 없이 운영 | 하. 동시편집과 감사로그가 불가능해 탈락 |

- **A안:** 가장 빨리 쓸 수 있습니다. 다만 OnlyOffice 무료판은 동시접속 20명 제한이 있고, AGPL 라이선스는 법무 검토가 필요합니다. 조문 단위 수락/거절을 붙이기도 어렵습니다.
- **B안:** 취합 흐름을 원하는 대로 만들 수 있습니다. 대신 유지보수가 개발자 1인에게 달리는 위험이 있습니다.
- **권장:** 파일럿은 B안 축소형으로 합니다. 범용 문서 편집은 A안과 병행할 수 있습니다.

## 3. 핵심 기능 (MVP)

### 취합 담당자
1. 원문 업로드 후 부서별로 담당 조문을 배정하고 마감일을 지정
2. 현황판에서 제출/미제출을 보고 미제출 부서에 독촉, 충돌 조문은 빨간 배지로 표시
3. 조문별로 **채택 / 불채택 / 검토중**을 누르고 사유 입력
4. **신구대비표 자동생성**(현행 / 개정안 / 사유 3단, 밑줄·취소선 표기)
5. 버전 스냅샷(1차안·2차안) 비교, 최종본을 HWPX·DOCX·PDF로 출력

### 부서 수정자
1. 링크를 누르면 **"우리 부서 담당 조문"만** 열림
2. 원문 위에서 바로 수정하면 한글의 변경추적처럼 표시
3. 사유는 한 줄로 입력
4. **[제출] 버튼 하나**로 끝(부서장 확인 포함)
5. 반영 여부 회신 확인

### 수정이력 표시 방식
- 추가는 파란 밑줄, 삭제는 빨간 취소선으로 표시하고 부서마다 고정 색을 줍니다.
- 조문 옆에 "이력 3건" 배지를 두고, 누르면 누가·언제·무엇을 바꿨는지 타임라인으로 보여줍니다. [이 버전으로 되돌리기]도 넣습니다.
- 버전 이름은 "v1.3" 대신 **"9/23 기획과 제출본"**처럼 알아보기 쉽게 붙입니다.

## 4. 권장 아키텍처 (B안 축소형)

```
[브라우저] TipTap 에디터 ── Yjs(동시편집) ── Hocuspocus 서버
                                              │
                                        PostgreSQL
   ├ 문서: 조문 블록 배열 (고유ID, 번호, 본문)
   ├ 제안(proposal): 조문ID, 부서, 원문해시, 제안문, 사유, 상태
   ├ 이력(revision): 누가, 언제, 이전·이후 내용
   └ 감사로그: 접속·열람·수정·다운로드 (1년 이상 보관)
```

- 부서 수정은 에디터 안에서 변경추적으로 처리하지 않습니다. **DB에 제안(proposal) 행으로 저장**합니다. 이렇게 해야 단순하고 안정적입니다.
- 수락 시점에 원문이 이미 바뀌었다면 원문해시가 달라지므로 **"재검토 필요"**로 표시합니다.
- 계정은 AD/LDAP 또는 SSO와 연동합니다.
- 설치는 외부에서 Docker 이미지를 만든 뒤 `docker save`로 tar 파일을 만들고, 망연계로 반입해 `docker load`로 설치합니다.

**개발 기간 (1인 바이브코딩 기준)**
- MVP: 6~10주
- 운영 수준(보안점검, 백업, 대용량 표 처리): 3~5개월

## 5. 핵심 리스크 Top 5

| # | 리스크 | 심각도 | 대응 |
|---|---|---|---|
| 1 | **HWP 호환.** HWP 바이너리는 쓰기가 사실상 불가능하고, 서식이 깨지면 사용자가 결국 한글로 돌아감 | 상 | 입력은 "한글에서 HWPX·DOCX로 저장 후 업로드". 출력은 HWPX 결재양식 템플릿에 채워 넣기. 파일럿 전에 표·각주·조문번호가 보존되는지 검증 |
| 2 | **폐쇄망 반입·보안성 검토.** 망연계, 백신검사, 해시검증, 구성요소 목록(SBOM) 제출, 업데이트할 때마다 반입 반복 | 중 | 오프라인 설치 번들을 표준화하고 시큐어코딩 점검(47개 항목)을 사전에 받음 |
| 3 | **공식 기록 근거.** 감사 때 "어디에 남았나"에 답하지 못하면 공문을 병행하게 되고, 이중작업이 되면 사용자가 이탈함 | 중 | 최종본과 신구대비표를 전자결재 첨부용으로 출력. 감사로그 보관 |
| 4 | **유지보수 인력 의존.** 담당자가 인사이동하면 방치됨 | 중 | 구조를 단순하게 유지(DB 중심), 운영 매뉴얼 작성 |
| 5 | **동시편집 신뢰 문제.** "내가 고친 게 사라졌다"는 경험 하나로 저숙련 사용자가 떠남 | 중 | 조문 단위 잠금("○○과 편집 중" 표시), 자동저장 표시 상시 노출 |

**인증 관련 정리**
- 공동편집기는 CC인증이나 보안적합성검증 대상이 아닌 경우가 대부분입니다.
- GS인증은 공공 납품에만 필요합니다. 사내에서 직접 만들어 쓰는 경우에는 불필요합니다.
- N2SF(국가망 보안체계) 기준으로 지침 개정안은 대부분 S(민감) 등급입니다. 업무망 내부 서버에서만 운영하면 됩니다.

## 6. 전문가 5인 검토 요약

| 전문가 | 판정 | 한 줄 의견 |
|---|---|---|
| 보안 (망분리·CISO) | 중 | Nextcloud+OnlyOffice 기반에 취합만 얇게 자체개발하고, 보안성 검토와 HWP 변환 검증을 먼저 받을 것 |
| 아키텍처 (협업편집) | 중상 | 핵심은 CRDT가 아니라 조문 단위 제안 관리. DB 중심으로 단순하게 설계 |
| 현업 실무 (기획·총무 20년) | 중 → 상 | 신구대비표 자동생성이 킬러 기능. HWP 입출력이 없으면 도입 논의 자체가 안 됨 |
| UX | 중 | 수정자는 링크, 수정, 제출의 3단계로 끝나야 함. 서식이 깨지면 즉시 이탈 |
| 사업화·조달 | 중 | 제품 판매는 하, 강의 실습 프로젝트로는 상 |

## 7. 권고 실행안

1. **범위를 한 가지로 좁히기:** "지침 개정 취합" 업무 하나만 합니다.
2. **MVP 8주:** 조문 분할, 부서 배정, 제안·수락, 신구대비표, HWPX/DOCX 출력.
3. **파일럿:** 1개 기관·1개 부서에서 한 번의 개정 주기 동안 실사용합니다.
4. **사업화 순서:** 유튜브 소재("메일로 한글 파일 돌리던 취합, 이렇게 끝냅니다") → 바이브코딩 강의 대표 실습 → 템플릿·소스 판매 → 수요가 검증되면 기업 맞춤 구축(B2B). 공공 조달은 협력사를 통해 진행합니다.
