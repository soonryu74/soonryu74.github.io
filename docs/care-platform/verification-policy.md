# 자격 확인 운영안

작성: 2026-10-05 · 상태: **운영 전.** 아래 절차를 수행할 담당자가 정해지지 않았다.
3차 지시서 §7-3 에 대한 답이다.

> **지금 화면에 확인 배지가 하나도 없는 이유** — 이 절차를 운영할 사람이 정해지지 않았기 때문이다.
> 사람이 원본 서류를 보기 전에는 어떤 표시도 붙이지 않는다. 자동 판정하지 않는다.

---

## 1. 무엇을 확인하는가

| 종류 | 대상 | 확인하는 것 | 원본 확인 경로 |
|---|---|---|---|
| 요양보호사자격 | 개인 | 자격증 원본 또는 자격 확인서 | 국시원 상시홈페이지 자격증 **진위 확인** |
| 간호조무사자격 | 개인 | 자격증 원본 | 국시원 상시홈페이지 자격증 **진위 확인** |
| 간호사면허 | 개인 | 면허증 원본 | 보건복지부·국시원 경로 |
| 교육이수 | 개인 | 보수·법정의무교육 수료증 | 발급 기관 조회 |
| 기관실재 | 기관 | 장기요양기관 지정 여부 | **장기요양기관기호**로 노인장기요양보험 조회 |
| 사업자등록 | 기관 | 사업자등록증 | 국세청 사업자등록 상태 조회 |

**확인하지 않는 것**: 인성·실력·평판. 과거 근무 이력의 사실 여부. 이런 것은 확인했다고 말하지 않는다.

## 2. 상태와 흐름

```
requested ──▶ in_review ──▶ verified ──▶ (유효기간 경과) expired
                   │                └──▶ revoked   (본인 요청·사후 결격)
                   └──▶ rejected  (사유 필수)
```

| 상태 | 뜻 | 화면 표시 |
|---|---|---|
| `requested` | 본인·기관이 확인을 신청함 | 표시 없음 |
| `in_review` | 담당자가 검토 중 | 표시 없음 |
| `verified` | **사람이 원본을 확인함** | 확인 표시 노출 |
| `rejected` | 확인되지 않음. **사유 필수** | 표시 없음. 사유는 본인에게만 |
| `expired` | 유효기간 경과 | 표시 사라짐 |
| `revoked` | 철회됨 | 표시 사라짐 |

데이터 구조에서 강제하는 것(격리 환경에서 검증함):

- `verified` 로 만들려면 **`reviewed_by` 와 `reviewed_at` 이 반드시 있어야 한다.**
  검토자 없이 확인 상태를 만들 수 없다. (제약 `verified_needs_reviewer`)
- `rejected` 로 만들려면 **사유가 반드시 있어야 한다.** (제약 `rejected_needs_reason`)
- 모든 상태 변경은 `verification_events` 에 **덮어쓰지 않고 쌓인다.** 트리거가 자동으로 기록한다.

## 3. 누가 하는가 — **미정 (사용자 결정 필요)**

| 역할 | 하는 일 | 현재 |
|---|---|---|
| 검토 담당자 | 원본 대조, 상태 변경, 사유 기록 | **정해지지 않음** |
| 검토 책임자 | 반려·철회 이의 처리 | **정해지지 않음** |
| 개인정보 보호 책임 | 증빙 보관·파기 | **정해지지 않음** |

담당자가 정해지기 전까지 `verified` 상태를 만들지 않는다. 이 문서의 절차는 담당자가 생기면 바로 쓸 수 있도록 미리 써 둔 것이다.

## 4. 증빙을 다루는 방법

- **증빙 파일을 이 데이터베이스에 넣지 않는다.** `verifications` 테이블에는 **보관 위치 참조(`evidence_ref`)와 해시(`evidence_sha256`)만** 둔다.
- 보관소는 공개 경로가 아니어야 한다. 운영 주체가 정해지면 접근 권한과 보관 기간을 함께 정한다.
- **익명·로그인 사용자는 증빙 참조·해시·검토자·사유를 읽을 수 없다.**
  열 단위 권한으로 막았고, 격리 환경에서 모두 `permission denied` 를 확인했다.
- 공개되는 것은 `verification_badges` 뷰의 네 가지뿐이다: `subject_type`, `subject_id`, `kind`, `valid_until`.

> 설계 중 발견한 함정 — 처음에는 기반 테이블에 테이블 단위 SELECT 를 주고 뷰로 가렸는데,
> **RLS 는 행을 거를 뿐 열을 가리지 않아** 증빙 보관 위치가 그대로 읽혔다.
> 열 단위 권한으로 바꿔 막았다. 같은 함정이 `caregivers.contact` 에도 있었고 따로 교정안을 준비했다
> (`db/migrations/pending-20261005-caregivers-column-exposure.sql`).

## 5. 재확인과 만료

- `valid_until` 을 둔다. 지나면 배지가 **자동으로 사라진다.** 운영자가 따로 지우지 않아도 된다.
- 권장 주기: 자격·면허 **1년**, 기관 실재 **1년**, 교육 이수는 해당 교육의 유효기간.
- 만료 전 안내를 보낼지는 운영 결정 사항이다(연락 수단·동의 범위가 걸린다).

## 6. 철회·이의제기

| 상황 | 처리 |
|---|---|
| 본인이 철회를 요청 | `revoked` 로 바꾸고 사유 기록. 배지 즉시 사라짐 |
| 사후에 결격이 확인됨 | `revoked` + 사유. 필요하면 프로필도 비공개 처리 |
| 반려에 이의 | 새 `verifications` 행을 만들어 다시 신청한다. **기존 행을 고치지 않는다** (이력 보존) |
| 확인 기록 열람 요청 | 본인 분에 한해 제공. 검토자 개인 식별정보는 제외 |

## 7. 화면에 쓰는 문구 규칙

- 확인된 경우: **"○○ 자격 확인됨 (확인일 YYYY-MM-DD, 유효 YYYY-MM-DD까지)"**
- 확인 전: **"자격 확인 전"** — '미인증'처럼 부정적으로 쓰지 않는다.
- **"인증", "보증", "검증 완료" 라는 말을 쓰지 않는다.** 모심·곁애는 서류를 대조했을 뿐 그 사람의 일을 보증하지 않는다.
- 광고 상품(프리미엄)과 자격 확인을 **같은 자리에 같은 모양으로 표시하지 않는다.**
