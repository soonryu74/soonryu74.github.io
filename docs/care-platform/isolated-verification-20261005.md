3차 지시서 §3·§6 에 대한 답이다. **운영 DB에서는 어떤 쓰기도 하지 않았다.**

## 1. 환경

| 항목 | 값 |
|---|---|
| 요청한 환경 | Supabase 개발 브랜치 (사용자 승인) |
| 결과 | **생성 실패.** `create_branch` 가 두 번 모두 60초 시간 초과했고 `list_branches` 는 계속 비어 있다. 원인은 확인하지 못했다(요금제 제한 또는 승인 대기로 추정) |
| 실제 사용한 환경 | **이 작업 컨테이너의 PostgreSQL 16.13** (포트 55432, `trust` 인증, 루프백 전용) |
| 스키마 | `tests/isolated/00-schema.sql` — 운영의 공개 스키마·정책·역할 체계를 재현 |
| 데이터 | **운영 데이터를 옮기지 않았다.** 모든 행은 `FIXTURE-`·`example.test` 로 식별 가능한 합성 데이터 |

### 재현 범위의 한계 — 그대로 보고한다

- **PostgREST 가 없다.** HTTP 계층(201/409/204 응답 코드, 자동 갱신 가능 뷰로 내려가는 DELETE)은 재현되지 않는다. SQL 계층의 권한·정책·제약 동작만 검증했다.
- Supabase 의 `authenticator` → `anon`/`authenticated` 역할 전환, JWT 처리, `auth.uid()` 는 재현하지 않았다. 역할은 `set role` 로 바꿨다.
- 따라서 **"격리 환경에서 통과했다"가 운영에서의 안전을 입증하지 않는다.** 운영 적용 후 다시 확인해야 한다.

실행:

```bash
psql -h 127.0.0.1 -p 55432 -U postgres -f tests/isolated/00-schema.sql
psql -h 127.0.0.1 -p 55432 -U postgres -f tests/isolated/10-roles.sql
psql -h 127.0.0.1 -p 55432 -U postgres -f tests/isolated/20-idempotency.sql
psql -h 127.0.0.1 -p 55432 -U postgres -f tests/isolated/30-waitlist-redesign.sql
psql -h 127.0.0.1 -p 55432 -U postgres -f tests/isolated/40-waitlist-verify.sql
```

## 3. 접수 중복과 정상 재시도 (§6)

### 3.1 기존 설계의 문제 — 격리 환경에서 재현됨

`tests/isolated/20-idempotency.sql`

| 시나리오 | 기존 동작 | 문제 |
|---|---|---|
| 같은 토큰·같은 내용 재시도 | `23505` | 사용자에게는 **실패로 보인다**. 수렴이 아니다 |
| 같은 토큰·**다른 내용** | `23505` | 위와 **구분되지 않는다**. 잘못된 키 재사용을 잡아내지 못한다 |
| 새 토큰·같은 연락처(대소문자만 다름) | `23505` | 의도대로 중복 차단 |
| **같은 번호, 다른 역할**(가족 공동 연락처) | `23505` | **🔴 정당한 접수가 막힌다** |
| 다른 경로(`source`)에서 같은 연락처 | 성공 | 의도대로 |

그리고 더 중요한 문제: **`23505`(409) 가 돌아온다는 사실 자체가 "그 연락처는 이미 등록되어 있다"는 신호**다. 공개 키만 있으면 누구나 시도할 수 있으므로 **화면 문구만 바꿔서는 막히지 않는다.**

### 3.2 재설계

`tests/isolated/30-waitlist-redesign.sql` → 운영 적용안 `db/migrations/pending-20261005-waitlist-submit-rpc.sql`

1. 연락처 유니크 범위를 **(정규화 연락처, 경로, 역할)** 로 좁힌다.
2. 접수를 **함수 `submit_waitlist`** 로만 받고, 테이블 직접 INSERT 권한을 회수한다.
3. 함수는 **새로 저장했든 이미 있든 항상 `'accepted'`** 를 돌려준다 → 열거 oracle 제거.
4. **요청 지문(sha256)** 을 저장해, 같은 토큰·같은 내용은 수렴시키고 **같은 토큰·다른 내용은 거부**한다.
5. 서버에서 역할 허용값·입력 길이를 검사한다.

함수는 `SECURITY DEFINER` 지만 앞서 제거한 `import_eval_chunk` 의 실수를 되풀이하지 않는다:
`search_path=''` 고정 · 동적 SQL 없음 · 대상 테이블 고정 · **외부 URL 요청 없음** · **어떤 행 데이터도 반환하지 않음**.

### 3.4 동시 요청

16개 psql 세션을 동시에 던졌다.

| 묶음 | 요청 | 응답 | 실제 저장 |
|---|---|---|---|
| 같은 토큰 ×8 | 동일 내용 | `accepted` ×8 | **1행** |
| 다른 토큰 ×8, 같은 연락처 | 동일 연락처 | `accepted` ×8 | **1행** |

총 16요청 → **2행**. 오류가 새어 나가지 않았고 중복도 생기지 않았다.

### 3.5 접수 여부 확인 수단

익명이 `waitlist` 를 되읽을 수 없으므로(그래야 한다), 사용자가 자기 접수를 확인할 방법이 따로 필요하다.

- 접수 성공 화면에 **접수 확인 번호**(`client_token`, `crypto.randomUUID()`)를 **한 번만** 보여준다.
- 이 값은 **URL·localStorage·로그에 넣지 않는다.** 화면에만 표시한다.
- 수정·삭제 요청 시 이 번호를 알려달라고 안내한다.
- **온라인 재조회 기능은 만들지 않았다.** 재조회를 만들면 토큰이 유출됐을 때 접수 내용이 통째로 노출된다. 운영 창구가 정해지면 그때 설계한다.

### 3.6 업무상 중복 범위 — 정한 것과 남은 것

| 대상 | 중복 단위 | 상태 |
|---|---|---|
| 곁애 사전등록(`waitlist`) | (연락처, 경로, **역할**) 당 1건 | 이번에 정함 |
| 모심 구직 프로필(`caregivers`) | `client_token` 당 1건만. 연락처 기준 중복은 **막지 않는다** (같은 사람이 직종을 나눠 올릴 수 있다) | 현행 유지 |
| 공고 지원 | — | **미설계** (공고 기능 자체가 없음) |

### 3.7 연락처 정규화 규칙

```
lower(regexp_replace(contact, '[^0-9a-zA-Z@.]', '', 'g'))
```

- 숫자·영문·`@`·`.` 만 남기고 모두 제거한 뒤 소문자로 바꾼다.
- `010-1234-5678` · `010 1234 5678` · `01012345678` → 모두 같은 값.
- `A@Example.Test` · `a@example.test` → 같은 값.
- 한글·공백·괄호·하이픈은 제거된다. 따라서 `카톡 abc123` 과 `abc123` 은 같은 값이 된다. **오픈카톡 아이디처럼 자유 형식 연락처에서는 의도보다 넓게 묶일 수 있다** — 알려진 한계로 적어 둔다.
- 저장되는 값은 **원본 그대로**다. 정규화는 인덱스 식에서만 쓴다.

## 4. 운영에 아직 적용하지 않은 것

| 항목 | 파일 | 이유 |
|---|---|---|
| 접수 함수·유니크 범위 변경 | `db/migrations/pending-20261005-waitlist-submit-rpc.sql` | `drop index`·`drop policy` 포함. 승인 필요 |
| 시험 흔적 정리 3건 + 함수 제거 | `docs/care-platform/cleanup-plan-20261004.md` | 승인 창에서 계속 막힘 |
